# AGENTS.md

Guidance for AI coding agents working on **LemonPie** (PyPI: `lemonpie-cli`).
Read this before making changes. Human contributors may find it useful too.

## Project overview

LemonPie is a lightweight chat CLI for any OpenAI-compatible inference server
(Ollama, llama.cpp, LM Studio, vLLM, and others). It manages chat sessions, persists
history locally, and streams responses. Design goals: few dependencies, small
footprint, works on low-power machines (e.g. Raspberry Pi OS Lite over SSH) and on
Linux, macOS, and Windows.

- Python `>=3.11`, licensed GPL-3.0-or-later
- Build: `hatchling` + `hatch-vcs` (version comes from git tags); managed with `uv`
- Runtime dependencies: `httpx2`, `platformdirs` (keep it this small)
- Entry points (`pyproject.toml`): `lm` and `lemonpie` -> `lemonpie.main:main`; `lmConfig` -> `lemonpie.cli.config_cmd:main`

## Knowledge base (`.agents/kb/`)

The KB is agent-facing documentation of what is **implemented today**. It is separate from
`docs/`, which is for users and developers.

- Before non-trivial work (new features, config schema, CI/release, session format), read
  `.agents/kb/INDEX.md` and open only the 1-3 notes relevant to the task.
- Source of truth for existing behavior, in order: code and tests, then the KB. If a note
  disagrees with the code, fix the note in the same PR.
- `docs/design/` holds the maintainer's proposals and brainstorming. It is **not** part of
  the KB and **not** a source of truth for existing code. Read it only when asked to build
  or review a feature designed there. When a design ships, document the result in the KB.
- Only document implemented behavior in the KB. Don't mirror design docs into it.
- Follow the update rules in `INDEX.md`: any note create, rename, or delete updates the
  registry and the topic's `_topic.md` in the same change; bump `updated` on edits.
- When removing or replacing something, delete it outright and remove every reference to it
  (code, docs, KB registry, `related:` ids, links, README tree). Never leave an
  "obsolete" tombstone. Finish by grepping the repo for the old names and paths.

## Setup and commands

```bash
uv sync                    # install deps incl. dev group (pytest)
uv run pytest              # run the test suite (must pass before any PR)
uv build                   # build sdist + wheel
uv run lm -v               # smoke test the CLI
```

- If `lm -v` shows a stale version after pulling tags, run
  `uv sync --reinstall-package lemonpie-cli` (hatch-vcs only regenerates on reinstall).
  A `.devN` suffix when not exactly on a tag is expected, not a bug.
- For wheel verification, install the built wheel into a throwaway env
  (`uv venv .test-env`, gitignored), never into the project env.
- CI pins `uv` to a specific version; keep local and CI behavior in mind when changing it.

## Configuration and runtime paths

- Config keys: `backend`, `server`, `api_key` (nullable), `default`, `models` (list of `{alias (nullable), name}`). Template: `docs/config.example.json`.
- Config and sessions live in OS-standard user directories via `platformdirs` (see `paths.py`). Never write to the repo directory at runtime.
- Environment overrides: `LEMONPIE_HOST`, `LEMONPIE_CONFIG_DIR`, `LEMONPIE_SESSION_DIR`.
- Changing the config schema is a breaking change for users. Treat it as one (see releases below) and update `docs/config.example.json`, the README, and `lmConfig --init`.

## Code conventions

- Don't add dependencies without a clear reason, and call it out explicitly in the PR.
- Writes to config/session files must be atomic (temp file, then replace).
- Handle Ctrl-C gracefully; streaming must not leave sessions half-written.
- Avoid import-time side effects (no config loading or client construction at module top level). `lm --help` must work with no config and no reachable server.
- Offline actions (`-l`, `-p`, `-d`, `-c`, `--delete-all`) must work without a configured model or a reachable server.
- `--dry-run` must never send requests or modify data. Any new action that sends a request or writes to disk has to respect it (and needs a case in `test_dry_run.py`).
- Don't hand-roll session dicts; go through `create_session()` so timestamps and IDs stay consistent (single timestamp snapshot, collision-proof IDs).
- Be backend-neutral. Don't hardcode Ollama-specific endpoints or behavior outside code paths that are explicitly gated on `backend`.
- Catch specific exceptions (e.g. `httpx2.ConnectError`, `TimeoutException`, `JSONDecodeError`), not bare `except`.
- Never edit `src/lemonpie/_version.py`.

## Testing

- Framework: `pytest`; config in `[tool.pytest.ini_options]` in `pyproject.toml`.
- Use the `isolated_dirs` fixture (`tests/conftest.py`) for anything touching config or sessions. Each module holds its own import-time copy of the paths, so the fixture monkeypatches `CONFIG_FILE` / `SESSIONS_DIR` / `CURRENT_FILE` in every module that uses them. If you add a module that imports these paths, add it to the fixture.
- An autouse `mock_argv` fixture keeps tests independent of the real `sys.argv`. Don't remove it; CLI tests broke in CI without it.
- Tests must not hit a real network or inference server. Mock HTTP and client calls.
- Fix bugs with a regression test. If you must defer a known bug, use `xfail(strict=True)` with the cause in `reason=`.
- `ci.yml` runs `uv build` then `uv run pytest` on pushes and PRs to `main`.

## Git, commits, and releases

Releases are automated with **release-please**; commit messages drive versioning, so
format matters.

- Use Conventional Commits: `feat:`, `fix:`, `perf:`, `deps:`, `refactor:`, `test:`, `docs:`, `chore:`, `ci:`, `build:`. Only `feat:`, `fix:`, `perf:`, `deps:`, `revert:` and breaking changes appear in release notes and trigger release PRs. `docs:`, `chore:`, `refactor:`, `test:`, `ci:` do not.
- Breaking changes use `feat!:` (or a `BREAKING CHANGE:` footer). While pre-1.0, a breaking config/CLI change bumps the minor version (as with 0.3.0).
- Work on a feature branch, open a PR to `main`, and **squash and merge** (`gh pr merge --squash`). Plain merge commits caused duplicate release-note entries.
- PR titles should follow Conventional Commits too: `pr-labler.yml` derives labels from them, and those labels group the GitHub release notes.
- Do not create or push version tags manually. Tags come from merged release-please PRs. Tags are plain `v{version}` (`include-component-in-tag: false`; do not change this, since hatch-vcs also only matches `v*`).
- To force a specific version (alpha -> beta -> rc -> stable), use a `Release-As: <version>` trailer in the commit message. Don't hand-edit `.release-please/manifest.json`.
- Pre-1.0 policy: each minor cycle goes alpha -> beta (stabilization only, no new scope) -> stable. A CLI-syntax-compatible feature starts the next patch cycle; a breaking rewrite starts the next minor.
- `release.yml` publishes to PyPI through OIDC trusted publishing (environment `pypi`) and runs tests first. Don't add long-lived PyPI tokens. The release-please action uses a repository token secret (`RELEASE_PLEASE_TOKEN`) so its PRs trigger CI; don't swap it for `GITHUB_TOKEN`.
- Workflow actions are pinned by commit SHA with a version comment. Keep that convention when touching workflows.

## Documentation

When behavior changes, update in the same PR:

- `README.md` (features, usage, project structure)
- `docs/usage/command-index.md` (command reference)
- `docs/ROADMAP.md` (remove items that ship) and the matching `docs/design/` page if the feature came from one
- the relevant `.agents/kb/` notes (and its `INDEX.md` registry)
- `docs/config.example.json` if the config schema changes

Use absolute links in `README.md`, since PyPI renders it outside the repo.

## Boundaries

- Don't run destructive commands (`--delete-all`, deleting sessions, force-pushes) against real user data. Use isolated dirs.
- Don't commit generated or local artifacts: `dist/`, `__pycache__/`, `.test-env/`, `_version.py`, `tests/pytest.log`, real config or session files.
- Don't bypass CI (`--no-verify`, skipping tests) to get a change through.
- If scope is ambiguous (new dependency, CLI syntax change, config schema change), propose the change first rather than implementing it.

## Environment notes

- Primary development is on Windows (also developed on Debian). Keep path handling and shell commands cross-platform; don't assume POSIX-only tools in scripts or tests.
- Local interpreter is CPython 3.14 via `uv`; the supported floor is 3.11, so avoid newer-only features.
